# 艦これ 終了予定通知

艦これの通常通信で受信した遠征・入渠・建造の終了予定Unix時刻（ミリ秒）を中央へ送り、Cloudflare Workersが毎分確認してTelegramへ通知します。同期後はPCを終了できます。

## 送信方式（0.2.0）

- プレイ開始時にUUID＋世代番号を取得。世代番号は64ビット整数を文字列で扱い、上限でUUIDを更新して1へ戻します。
- 初回は取得できた予定・空き状態を送信。その後は変更・取消のある対象だけ送信します。
- 終了予定時刻を補正しません。時計同期・5分ごとの定期通信はありません。
- 古いプレイの送信は中央で拒否。同一世代の連番で重複・逆順を除外します。再送で世代を取り直しません。
- 同期応答に予約・履歴を含め、画面は端末内キャッシュで更新。中央への追加取得は設定の接続確認と更新ボタンのみです。
- 通信失敗時は送信待ちを保存し1、2、4、5分間隔で再送します。世代未取得の場合は次のゲーム情報受信時に取得を試みます。
- 手動予約・取消は操作時に送信。受理結果不明の手動予約は同じIDで確認・再送します。
- 取得には対象タブのDevToolsが必要。api_start2系の受信をプレイ開始として扱い、途中で取得機能を開いた場合は最初の正常な対象通信から開始します。
- ゲームへの追加リクエストやKC3の変更はありません。解析対象外・失敗した応答から取消を作りません。

## 予定表示・疲労回復（0.3.0）

- ポップアップは遠征・入渠・建造、艦隊の疲労回復、手動予約を表示します。送信内容・送信待ち・履歴は「予約と履歴」へ移しました。
- 「あと何分／何時に」はセグメントコントロールで切り替え、端末内に保存します。残り時間の更新は表示だけで通信しません。時計の経過補間は表示専用で、中央の通知判定には使いません。
- 疲労回復の目標は設定で登録した数字だけを表示します。固定の既定値・プリセットはありません。0～100の整数を重複なしで最大12件登録でき、既定値は登録済みの選択肢から指定します。空欄は未設定です。
- 艦隊ごとの選択と設定は各端末に保存します。選択中の数字を設定から削除するとその艦隊は既定値を使います。目標変更で予約が変わった場合だけ中央へ送信します。
- 疲労回復は受信した艦のcond、編成、入渠、補給、備蓄燃料とゲーム応答のHTTP Dateから推定します。自然回復は3分で3、上限49の遅めの見込み。観測前の回復周期が不明なため最大約3分の誤差があります。
- 母港給糧は野埼・野埼改の旗艦／2番艦配置を扱い、給糧艦自身を対象から除きます。15分の共通タイマー、回復量2／3、上限54、補給・損傷・cond・入渠・燃料の条件を確認します。自然回復が先に完了してからの給糧を見積もるため、余裕を持った時刻になります。
- 通常の編成変更で給糧開始時刻を記録。編成プリセットと随伴一括解除は既存タイマーを維持します。母港で15分以上経過していれば共通タイマーを更新します。途中から取得して開始時刻が分からない場合は未計測です。
- 給糧の条件が今後も続く前提の見込みであり、母港での反映確認が必要です。間宮・伊良湖の効果は予測せず、使用後に受信した母港の実値から再計算します。出撃・演習・改装などで状態が不確かになった間は予約を解除し、母港で再計算します。
- 目標未設定、時刻・状態不足、入渠／遠征中、回復上限超過などは理由を表示し予約しません。自然回復・給糧の見込みは中央で通知します。ゲームに追加リクエストを送りません。
- 仕様確認資料：[KC3Kai](https://github.com/KC3Kai/KC3Kai)、[母港給糧艦システム（運営告知の引用とコミュニティ検証）](https://wikiwiki.jp/kancolle/%E9%87%8E%E5%9F%BC#FoodSupplyShip)。ゲーム更新時には条件の再確認が必要です。

## ローカル実行

Node.js 24で `npm.cmd run dev`。疑似環境は `http://127.0.0.1:8787/mock`。
端末トークンは `.local/devices.json`。DBは `.local/state.sqlite`。
模擬通知は `.local/notifications.jsonl` に記録し、Telegramには送りません。
新方式への切替時は予約状態を初期化します。旧データの変換・互換処理はありません。

疑似ゲーム環境（`/mock`）では、DevToolsを開いた状態で以下の疑似APIをブラウザ上で発生させ、拡張機能の受動監視・解析とポップアップへの反映をテストできます：
- ゲーム起動マスタ（`api_start2`）
- 母港帰投・疲労度・艦隊編成（`api_port/port`）
- 遠征情報（`api_get_member/deck`）
- 入渠ドック（`api_get_member/ndock`）
- 建造ドック（`api_get_member/kdock`）
- 操作回数とゲームAPI受信件数の比較により、余分な通信が発生していないかも常時監視されます。

## 本番更新

`npx.cmd wrangler deploy --config=wrangler.jsonc` で公開し、
`npx.cmd wrangler d1 execute kancolle-notify --remote --file=server/reset-reservations.sql --config=wrangler.jsonc` で既存予約を破棄して空の状態から開始します。この初期化は方式切替時だけ行い、通常の更新では実行しません。
拡張は再読み込みし、ゲームの通常通信から取得を再開してください。旧方式の端末内送信待ちは引き継がず、通常通信で最新状態を取得し直します。
旧/v1 APIは提供しません。中央の旧予約と通知待ちは破棄します。Secretと過去の監査履歴は保持します。


初期設置はD1にserver/schema.sqlを適用し、DBバインディングを設定します。
SecretはDEVICE_TOKENS（端末名→SHA256ハッシュのJSON）、TELEGRAM_BOT_TOKEN、TELEGRAM_CHAT_IDです。
`node tools/device-token.js windows` / `mint` で個別トークンを作成できます。
本番URLと `.local/windows.json` または `.local/mint.json` のtokenを各端末の拡張設定へ入力します。

## 通知と履歴

中央が終了予定以上の時刻になった時、毎分の確認回でまとめて通知します。通常は約0〜60秒の待ちがあります。
通知結果・変更・エラーの履歴はD1に30日保存し、ゲーム通信全文は保存しません。
有効な予約、プレイ識別、通知の再送情報は履歴期限で削除しません。
Telegramの認証・送信先エラー時は配信停止。設定修正後に「配信設定修正後に再開」を押します。
外部送信の応答消失時は再送するため、例外的に重複する可能性があります。

## 検証

`npm.cmd test` と `npm.cmd run check`。疑似ゲームへの追加通信ゼロ、変更なし時の中央通信ゼロ、PC切替・再送・桁あふれ、予約初期化を検証します。

## 泊地修理（0.4.0）

- ポップアップにクレーンアイコン付きの泊地修理欄を追加しました。各艦の周期開始HP→現在の推定HP、累計回復量、残り分数、日本時間の全回復予定時刻を表示します。全回復見込み時刻に達すると「全回復」に置き換えます。
- 通知は開始から20分経過時、および各艦が全回復する見込みの時刻です。1隻でも全回復すれば通知し、途中のHP増加では通知しません。通知には同じ艦隊の対象艦の現在の推定HPを併記します。
- 20分と全回復が重なる場合は1通にまとめます。中央の毎分確認で配信するため通常0〜60秒程度の待ちがあります。PC停止後も保存済みのデータから通知します。
- ローカルKC3の回復量計算と丸め処理を参考にし、2番艦の修理艦による0.85補正も扱います。母港での実際の反映を確認した値ではありません。
- 通常の編成変更から共通タイマーを開始し、プリセット・随伴一括解除では稼働中のタイマーを維持します。20分経過後の母港観測で次周期へ更新します。
- 途中監視、開始時刻・装備・艦情報不足は未計測として表示します。戦闘や装備変更などで条件が不明になれば予約を解除します。装備変更後など開始を確定できない場合は、情報取得後の通常編成変更で計測を開始します。
- 実装・検証・運用とも艦これへの追加リクエスト、ポーリング、自動操作はありません。通常プレイで受信済みの情報だけを使用します。
- ローカルの `/mock` に「泊地修理（20分経過・1隻全回復）」を追加。ボタンはlocalhostにだけ4件の模擬APIを発生させます。模擬応答のDateを20分前にし、20分待たずに表示・通知を検証できます。
- 本番利用には中央Workerと拡張の両方を更新してください。予約DBの初期化は不要です。
